# 多角色评审与 Readiness 定义

## Readiness 三级（门禁输出用，代替"通过/不通过"）

| 等级   | 定义                                                 | 下一步                      |
| ------ | ---------------------------------------------------- | --------------------------- |
| 草稿   | 核心要素缺失：目标不可证伪，或 AC 不可测，或范围未定 | 补全后重审                  |
| 待澄清 | 骨架完整，但「待确认」非空或存在 `[推测]` 级关键假设 | 用户答复或显式接受默认值    |
| 可开发 | Verification 自检全部通过，仅余用户拍板              | 用户确认 → status: approved |

## 多角色评审（L3 强制，L2 选用）

同一份需求，不同职能看到的风险完全不同。逐角色过一遍，每个角色至多输出 2 条**最高风险**的发现（贪多会稀释注意力），并标注 `[证据]`/`[推测]`：

**PM 视角**

- 机会是否真实：有用户反馈/数据支撑，还是拍脑袋？
- 假设是否可证伪：做完之后，用什么判断"做对了"？

**工程视角**

- 技术依赖是否明确：依赖的接口/服务/数据契约都确认可用了吗？
- 上线路径是否完整：灰度、回滚、迁移顺序写清楚了吗？

**数据视角**

- 预期变化是否可测：现有埋点够吗？需要新增吗？
- 判断口径是否会被污染：相邻改动/季节性会干扰结论吗？

**设计视角**

- 用户旅程是否完整：入口在哪、出错时用户看到什么、空状态长什么样？
- 边界情况：超长内容、无数据、弱网。

**运营 / 客服视角**

- 是否新增人工流程：需要 SOP 或后台工具吗？
- 用户问起来，客服答得上来吗？

**安全 / 合规视角**

- 是否触碰权限、隐私、计费、对外承诺？
- 是否有需要法务/合规确认的表述？

## 汇总规则

各角色发现可能互相冲突（如 PM 要快、工程要稳）。冲突不要自行裁决——原样列入 spec.md 第 8 节「待人类决策的问题」，附两边的代价说明。门禁的价值在于让冲突提前可见，而不是替用户做取舍。
