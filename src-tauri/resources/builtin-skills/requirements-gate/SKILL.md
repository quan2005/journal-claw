# 需求门禁 Requirements Gate

返工的根源大多不是代码写错，而是需求有歧义、缺上下文、假设未声明。在写代码前暴露这些问题，成本是分钟级；之后暴露，是天级。

## 三条原则

1. **先检索，再评审。** 未检索仓库就给的建议只是通用 PM 话术。每条判断标注 `[证据]`（附文件路径）或 `[推测]`。
2. **不给判决。** 不输出"通过/不通过"或评分，只输出 readiness、缺口、待人类决策的问题。拍板的是用户。
3. **spec.md 是契约。** 后续独立 subAgent 据此机械核对实现。AC 编号稳定、每条独立可测、非目标明确——否则无法核对。

## 分级

| 级别 | 适用 | 动作 |
|---|---|---|
| L0 跳过 | 非开发请求；已有 approved spec 的任务延续；用户标注 `[skip-gate]` | 正常响应 |
| L1 轻量 | 琐碎修复：typo、文案、单行 bug | 简版 spec，不问澄清问题，留档即执行 |
| L2 标准 | 常规功能开发/变更 | 完整流程 Step 1–7 |
| L3 深度 | 触碰任一项：数据契约 / 权限模型 / 计费定价 / 对外 API / 不可逆迁移 / 跨团队指标 | 完整流程 + L3 附加项 |

判级规则：
- **L3 条件优先于一切**：哪怕只改一行计费配置，也是 L3。其余拿不准时取高。
- 判断"任务延续"须 glob `specs/*/spec.md` 核对 frontmatter status，不凭记忆。
- 一次输入含多个独立可交付的需求：拆开，各走各的门禁。
- L1 简版 spec = frontmatter + 一句话背景 + 1–2 条 AC + 一行非目标，其余章节省略。status 直接置 approved（source: gate-L1），告知用户后即可动手，用户可事后否决。
- 用户中途要求跳过：尊重决定，当前草稿存档（status: skipped-by-user），附一行风险提示后执行，不重复劝阻。

## 流程

### Step 1 — 检索
用 rga（不可用则退回 grep / Grep 工具）检索：仓库相关模块与配置、`specs/` 下历史 spec、CLAUDE.md/docs 既有约定。证据 = 文件路径 + 一句话结论，写入 spec 第 7 节。检索为空也是信息——全新领域，假设风险更高。

### Step 2 — 模糊性清除
扫描需求原文中的模糊表达（无主体 / 无度量 / 无边界 / 隐含假设 / 无失败定义）。上下文已有明确定义的不算模糊。每处输出四件套：

> 原文：「支持批量操作」
> 类型：无边界 + 无失败定义
> 风险：批量上限与部分失败语义未定，线上才暴露
> 澄清：上限多少？部分失败 (a) 整体回滚 (b) 跳过并报告？
> 改写：「单次上限 100 条 [推测]；部分失败跳过并返回明细」

只说"这里不清楚"是失职；给出可直接替换进 spec 的改写才算完成。

### Step 3 — 缺口扫描
- **NFR**，按维度过一遍：性能 / 安全权限 / 数据隐私 / 可靠性降级 / 可观测性 / 回滚 / 兼容性 / 成本 / 风控滥用 / 运营客服 / 多语言地区。不适用写 N/A + 原因，不留空。
- **依赖与影响面**：依赖哪些系统/接口/数据契约？影响哪些模块/指标？与 Step 1 检索到的历史结论是否冲突？

### Step 4 — 路由
- **方案级未知**（目标不明、多方向、用户没想清楚）→ 交棒 brainstorming 技能，把 Step 1–3 的证据和缺口清单一并带过去。该技能不可用时降级：门禁在当前对话内按「目标—选项—取舍」自行引导，source 标 gate-degraded。
- **参数级缺口**（方向明确，缺上限/默认值/取舍）→ 直接澄清：一轮最多 5 个选项题，有合理默认值的不问。
- 用户跳过的问题：显式默认值 + 写入「待确认」，**绝不静默假设**。

### Step 5 — 产出 spec.md
按 `assets/spec-template.md` 撰写；brainstorming 产出的拿回来补全结构即可，**不退回返工**。位置：沿用 brainstorming 的输出约定，无约定则 `specs/<YYYYMMDD>-<slug>/spec.md`。

状态机：`draft`（撰写中）→ `clarifying`（澄清问题已发出，等用户）→ `approved`（用户确认）。后续 implemented/verified 由验证环节维护，本技能不触碰。

AC 规则：每条为「当 {前置}，执行 {操作}，应 {可观察结果}」；编号一旦发出不复用不重排，删除标 `[已废弃]`。

### Step 6 — 判定
向用户输出（一屏内）：
1. Readiness：**草稿**（核心要素缺失）/ **待澄清**（骨架完整但有待确认项）/ **可开发**（自检通过，仅余拍板）
2. 按风险排序的 3–5 个缺口（带 `[证据]`/`[推测]`；L3 多角色发现超量时，全量入 spec，此处只呈现前 5）
3. 待人类决策的问题 + 「待确认」默认值摘要

用户回复"确认/通过/可以开发"= 整体接受所有默认值，status 置 approved。用户要求修改 → 回 Step 2/5 增量更新，门禁记录加一轮。**approved 前不写任何实现代码；沉默不等于确认。**

### Step 7 — 交棒
接 writing-plans 或 spec-kit `/plan`（均不可用则直接开发），spec.md 路径写进开发计划首行。验收由独立 subAgent 依 AC 与非目标核对，本技能只负责留好契约。

## L3 附加项

1. **多角色评审**：PM / 工程 / 数据 / 设计 / 运营客服 / 安全合规，每角色至多 2 条最高风险发现，不适用的角色 N/A + 原因。角色间冲突不自行裁决，原样列入第 8 节附两边代价。
2. **NFR 强制项**（对应行不允许 N/A）：数据契约→兼容性、回滚；权限→安全、可观测性；计费→成本、风控、隐私；对外 API→兼容性、性能、安全；不可逆迁移→回滚（须含失败处置预案）；跨团队指标→可观测性（埋点口径与归因）。

## 想抄近道时读这里

| 借口 | 纠正 |
|---|---|
| "需求很简单" | 简单 → L1 留档，不是跳过。"简单"本身是未验证的假设 |
| "用户很急" | 急 → 问得更少、默认值给得更果断，而不是不问 |
| "我理解用户的意思了" | 理解 ≠ 共识。写下来被确认过的才是共识 |
| "上下文够了" | 没有检索记录就是不够。证据 = 文件路径，不是感觉 |
| "先替用户猜个方案" | 方案级未知交棒 brainstorming，门禁不替用户发明需求 |
| "用户没回，先做了再说" | 显式默认值 + 待确认，让假设可见、可推翻 |

## approved 前自检

- [ ] 每条 AC 独立可测、结果可观察、编号唯一
- [ ] 模糊表达已全部改写或列入「待确认」
- [ ] 非目标非空；NFR 每行有值或 N/A+原因（L3 强制行无 N/A）
- [ ] 依赖与影响面附文件路径证据；判断均有 `[证据]`/`[推测]` 标注
- [ ] 「待确认」已清零或被用户整体接受

自检全过 = 可开发。approved 的触发条件是用户显式确认，不属于自检项。
