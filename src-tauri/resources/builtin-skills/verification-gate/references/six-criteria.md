# 六字标准操作化 Six Criteria

"不漏不重不偏不倚不多不少"不是口号，每个字对应一种具体的核对动作和明确的 fail 判据。核对的铁律：**每条结论必须附证据（`文件:行` 或可复现的命令/测试输出），找不到证据就是 fail，不脑补"应该实现了"**。

| 字 | 回答的问题 | 核对方法 | fail 判据 |
|---|---|---|---|
| **不漏** | 每条 AC 都有对应实现吗 | 建 AC → 代码位置映射表，用 rga/grep 逐条定位 | 任一 AC 找不到实现位置 |
| **不重** | 有没有重复实现同一条 AC 的冗余 | 检查同一行为是否存在多套并行实现、复制粘贴路径 | 同一 AC 对应多处独立实现且无声明的原因 |
| **不偏** | 实现行为符合 AC 描述的预期吗 | 按 AC 的"当 / 执行 / 应"三段逐项比对；必要时运行测试或命令取证 | 实际行为与"应 {可观察结果}"不符 |
| **不倚** | 是否偏向某些 AC 而敷衍其他 | 横向比较各 AC 完成度：有没有 TODO / stub / 静默降级 | 任一 AC 处于占位或半成品状态 |
| **不多** | 有没有超出范围/非目标的实现 | diff 逐块归属：每个改动块归到某条 AC、范围条目或必要基础设施；归不进的列为越界 | 命中 spec 非目标，或存在无法归属的功能性改动 |
| **不少** | 范围内功能完整吗 | spec 第 3 节（范围）逐条对照——AC 未显式覆盖的范围条目也要核对 | 任一范围条目无对应实现 |

## 判定规则

- `result: pass` 需六项**全部**通过
- 任一项 fail → `result: fail`，并给出按风险排序的修复建议
- 灰色地带（最常见是"顺手的小改动"这类轻微越界，或与 AC 字面有出入但疑似更合理的实现）：**不替用户裁决**。列入报告「待用户裁决」一节，写清两边的代价；结论按保守原则计 fail，等用户表态——接受则回写 spec 后视为通过，不接受则修复

## 容易误判的三个点

1. **重构类改动**：纯等价重构（行为不变）可归为"必要基础设施"，不算越界；但带行为变化的"重构"必须能归属到某条 AC，归不了就是越界。
2. **不漏 ≠ 不偏**：找到了实现位置只满足"不漏"；行为对不对要单独比（不偏）。两步不能合并。
3. **AC 与范围的关系**：AC 通常覆盖范围，但 spec 写作疏漏时范围条目可能没有对应 AC——"不少"以范围为准兜底，并在报告中建议补 AC。
