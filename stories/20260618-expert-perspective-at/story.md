# @ 专家视角对话机制

> 一句话概括：**为需要高频获取不同专家洞察的知识工作者，解决专家 Skill 分散、无法在 JournalClaw 对话中自然召唤的问题。**

## 用户故事（Connextra）

作为 **频繁整理信息、复盘问题、做判断的知识工作者**，
当我 **面对产品方向、方案写作、会议复盘或复杂问题拆解，需要不同专家视角时**，
我希望 **能通过输入 `@专家名` 或点击画像列表中的 `@` 直接召唤对应专家视角进入对话**，
以便 **不用反复手写专家 prompt，也能像找教授讨论一样获得不同视角、挑战和洞察**。

## 真实用户问题（背景，讲故事）

用户已有一批不同专家的 Skill，也会在需要高质量观点时找真人聊，尤其偏好学校教授那类观点犀利、能挑战假设的对话。[证据: 用户访谈 2026-06-18]

现状的失败点有两个：第一，真人对话质量高，但不可随时获得，也不适合日常高频小问题；第二，专家 Skill 分散在 JournalClaw 外部，不能在对话里像 `@文件` 一样自然使用。[证据: 用户访谈 2026-06-18]

JournalClaw 已有画像系统，定位是让 AI 理解人物、项目、概念上下文；也已有 Skill 机制，支持通过 `SKILL.md` 提供处理流程和对话规则。[证据: docs/guide/profiles.md; docs/guide/skills.md] 但当前 `@` 更偏工作区文件引用，缺少“召唤一个可运行专家视角”的用户语义。[证据: src/components/AtMentionMenu.tsx; src/components/ChatPanel.tsx]

### 现状失败模式

- 用户现在怎么解决：手写 prompt 或手动使用分散在外部的专家 Skill；需要强观点时找真人教授交流。[证据: 用户访谈 2026-06-18]
- 为什么不够好：手写 prompt 有重复成本；外部 Skill 不能在 JournalClaw 对话中自然 `@`；真人专家不可随时获得，无法覆盖高频小问题。[证据: 用户访谈 2026-06-18]
- 支撑反馈：用户明确希望将已有专家 Skill 内置为专家库，并在画像列表中直接点 `@` 立刻生效。[证据: 用户访谈 2026-06-18]

## 成功标准（脊柱 Q4）

### 用户行为变化

做完后，知识工作者会：
- **专家召唤成本下降**：从“手写一段专家 prompt / 手动粘贴 Skill”变成“输入 `@专家名` 或点击画像列表 `@` 即可进入该专家视角”。
- **专家查找效率提升**：从“在外部分散 Skill 中寻找和组织 prompt”变成“30 秒内找到并 `@` 到目标专家”。

⚠️ 假设依据：以上基于用户直觉与当前访谈。首版将通过用户自测典型场景验证：是否能在 30 秒内找到目标专家并让下一轮对话进入对应视角。

## 验收标准（Given-When-Then）

### AC-1 — 输入框 @ 专家名召唤专家视角
- **Given** 当前工作区存在可用专家视角
- **When** 用户在对话输入框中通过 `@专家名` 选择一个专家并发送问题
- **Then** 下一轮 AI 回答应进入该专家对应的视角和对话协议
- **And** 用户不需要手写或粘贴该专家的 prompt

### AC-2 — 画像列表 @ 直接让专家视角进入当前对话
- **Given** 用户正在浏览画像列表，且其中某个画像可作为专家视角使用
- **When** 用户点击该画像上的 `@`
- **Then** 当前对话输入区应出现可发送的专家引用，或当前对话应以同等可见方式获得该专家引用
- **And** 用户发送后，下一轮 AI 回答应按该专家视角生效

### AC-3 — 专家作为单一分类可被查找
- **Given** 用户想从多个专家中选择合适视角
- **When** 用户通过 `@` 查找专家
- **Then** 用户应能在一个统一的“专家”分类中找到可召唤专家
- **And** 不要求用户按产品、架构、商业、设计、写作等细分类别继续筛选

### AC-4 — 30 秒内找到并 @ 到专家
- **Given** 用户知道自己想要某类专家视角，例如产品、架构、商业或教授式批判视角
- **When** 用户从对话或画像入口开始查找
- **Then** 用户应能在 30 秒内找到并 `@` 到一个合适专家

### AC-5 — 专家回答提供视角差异和洞察
- **Given** 用户已 `@` 某个专家视角并提出复杂问题
- **When** AI 生成回答
- **Then** 回答应体现该专家的思考框架、关注点或追问方式
- **And** 回答不应只是泛泛赞同用户，应能给出盲点、反观点、挑战性追问或明确判断中的至少一种

### AC-6 — 普通文件 @ 行为不被破坏
- **Given** 用户仍然需要 `@` 工作区中的普通文件、日志或材料
- **When** 用户选择普通文件引用并发送
- **Then** 原有文件引用语义应保持可用
- **And** 普通文件不应被误识别为专家视角

### AC-7 — 可清除当前会话专家视角
- **Given** 当前对话已经持续带有某个专家视角
- **When** 用户通过 `@` 选择“清除专家视角”并发送
- **Then** 当前会话应移除已挂载的专家上下文
- **And** 后续回答不应继续沿用被清除的专家视角，除非用户再次 `@` 专家

## 三类边界（脊柱 Q5 · Won't）

- **不为哪些用户做**：首版只服务单人知识工作者，不做团队共享专家库、组织权限、多人协作分发。
- **不在哪些场景出现**：首版覆盖对话输入框 `@` 和画像列表中的 `@` 操作；不要求在日志自动整理、会议转写、自动化任务、全局搜索、详情页阅读模式中自动触发专家视角。
- **不解决哪些相关但不同的问题**：首版不做多专家辩论、不做专家 Skill 自动蒸馏、不做专家市场/安装管理、不做从零生成专家 Skill 的完整 Nuwa 流程；专家内容来源优先复用已有 Skill 和内置专家库。

## 交棒清单（移交 design.md 的实现层问题）

- [ ] 专家视角的数据来源：已有全局/项目 Skill、内置专家库、画像文件，三者如何映射与去重？
- [ ] 专家分类的数据契约：首版只有一个“专家”分类；别名、触发词放在 Skill frontmatter、画像 frontmatter，还是单独索引？
- [ ] `@` 候选如何同时展示普通文件、画像、专家而不造成混淆？
- [ ] 画像列表点击 `@` 后，是插入可见引用等待用户发送，还是直接把专家上下文挂入当前会话？
- [ ] 专家视角如何进入 LLM：自动调用 `load_skill`、注入临时 Skill 内容，还是构造专门的专家上下文层？
- [ ] 如何保证专家视角只影响对应轮次/会话，不污染后续无关对话？
- [ ] 专家回答质量如何测试：是否需要固定测试 prompt 检查挑战性追问、反观点和专家差异？
- [ ] 普通 `@文件`、`/skill` 和专家 `@` 的优先级、冲突处理和回退提示。
- [ ] 内置专家库的初始专家清单、分类命名和是否从用户现有 Skill 迁移。

## INVEST 自检（输出闸记录）

- [x] **I** Independent：可作为专家召唤机制独立开发，不强依赖多专家辩论或 Nuwa 自动蒸馏。
- [x] **N** Negotiable：专家来源、注入方式、分类契约交给 design.md 决策。
- [x] **V** Valuable：直接降低用户获得专家视角的召唤成本。
- [x] **E** Estimable：核心入口、成功标准、边界已明确；仍需设计层确定数据契约。
- [x] **S** Small：首版限定在对话 `@` 与画像列表 `@`，切掉市场、辩论、自动蒸馏。
- [x] **T** Testable：AC 覆盖输入框、画像列表、分类查找、30 秒查找、专家回答质量与普通文件回归。
