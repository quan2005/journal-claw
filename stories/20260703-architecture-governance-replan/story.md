# 架构治理重规划：全景技术设定 + 落地清理

## 用户故事

作为本项目唯一的维护者 + AI 编排者（Leader 模式：Claude 规划、opencode 执行、Claude 验收），
我需要一份权威、全景、与重做后代码完全一致的技术设定体系，并把由此暴露的架构债清理掉，
以便后续每次规划/分发/验收不再重新考古，AI 执行者的产出质量稳定可预期。

## 背景与失败模式（证据）

项目已完成"彻底重做"（M8-b 终局：删 Rust/Tauri，Electron + TS daemon + pi 引擎，pnpm monorepo）。当前维护的四个具体失败：

1. **规范散落、执行不一致**：约定分散在 CLAUDE.md / docs/ARCH.md / docs/DESIGN.md / docs/final-state.md / 6 份 ADR / 15+ 个 stories 目录，AI 执行者常找不到或不遵守，产出质量不稳。[证据：约定重复出现且措辞不一，如 runtime 单一入口在 CLAUDE.md 约束 6 与 ARCH.md 前端边界各写一遍]
2. **架构债与结构漂移**：重做后残留旧结构，如 `apps/web/src/lib/tauri.ts` 兼容 shim（Tauri 已删除但 shim 仍是"单一入口"）、已下线能力的文档/入口残余；工作区还有 46 个文件未提交改动，代码与文档不完全一致。[证据：git status + ARCH.md 仍引用 tauri.ts]
3. **质量护栏不够硬**：测试/lint/CI 覆盖不均（如 `useAgentRun` 无专门测试，见 final-state.md），改动易破坏既有行为，验收依赖人肉。
4. **缺全景技术地图**：没有一份"唯一权威"的技术设定总纲，每次规划都要跨多文档考古拼图。

## 成功标准（Q4：做完后什么变了）

- 维护者规划任何新任务时，从**一个入口文档**出发 ≤2 跳即可找到所有相关约定，不再需要跨 6+ 文档考古。
- AI 执行者（opencode）接到任务说明后，产出违反既有架构约定的返工率显著下降（目标：验收一次通过率从当前的约一半提升到 ≥80%，以后续 10 个任务的 verify-report 统计）。
- 代码结构与文档描述一致：文档中引用的每个文件/边界在代码中真实存在且语义相符。
- 质量护栏机器化：约定尽可能转为 lint 规则 / CI 检查 / 测试，违反即红。

## 验收标准（GWT）

- **AC-1 全景技术地图**：Given 维护者打开技术设定入口文档，When 查找任一层面的约定（架构边界/工程规范/设计规范/流程门禁），Then 能在 ≤2 次文档跳转内到达该约定的唯一权威出处，且全体系无相互矛盾的重复表述。
- **AC-2 文档与代码一致**：Given 治理完成后的任一核心文档（ARCH/DESIGN/CLAUDE.md/final-state），When 核对其中引用的文件路径、模块边界、能力状态，Then 与代码库实际状态一致，无引用已删除/已改名的实体。
- **AC-3 架构债清单落地**：Given 分析产出的架构债清单（含 tauri.ts shim 处置、死代码、未提交改动归置），When 逐项执行完成，Then 每项有对应 commit 且 `pnpm -r test`、`pnpm build`、lint 全绿。
- **AC-4 护栏机器化**：Given 新增的自动化护栏（lint 规则/CI 检查/依赖边界检查），When 提交一个故意违反架构约定的改动（如组件直连 daemon URL），Then 本地或 CI 检查失败并给出可读的错误信息。
- **AC-5 分发可用性**：Given 治理后的技术设定，When 向 opencode 分发一个新任务，Then 任务说明可直接引用设定文档中的具体章节作为约束，无需在任务里重新解释架构。

## 三类边界（Won't）

- **不为谁**：不面向外部贡献者/开源社区的 onboarding 文档（README 只做一致性修正，不重写）。
- **不做哪些场景**：不做新产品功能开发；不改变产品北极星与五个一等对象的定义；不引入新技术栈（不换框架/构建工具/包管理器）；不做大规模 API 重设计——只清理债务、固化现状、补护栏。
- **不解决哪些相关问题**：不处理已下线的语音/转写能力回归；不处理 release/发布渠道策略；性能优化不在本次范围（除非是明显死代码删除的副产品）。

## 交棒清单（→ design.md）

1. 文档体系目标结构：入口文档选型（AGENTS.md 作 hub？新增 docs/CONVENTIONS.md？）、各文档职责切分与去重方案。
2. tauri.ts shim 的处置方案（保留改名 / 逐步内联 / 一次性替换）及影响面评估。
3. 护栏机器化技术选型：eslint 自定义规则 vs dependency-cruiser vs 简单 grep-based CI 脚本。
4. 46 个未提交改动的归置策略（属于哪个 story、是否先提交再治理）。
5. 任务拆解粒度与 opencode 分发批次规划（哪些可并行）。
6. 测试补齐优先级（useAgentRun 等已知缺口 vs 全面盘点）。

## 门禁判定

- Readiness：**可开发**（用户 2026-07-03 批准）
- 角色分工（用户拍板）：Claude 规划与拆解；opencode 执行；**kimi 独立验收**；Claude 终审合并。
- 未提交改动处置（用户拍板）：交 kimi 检查，没问题就提交。
