# Workspace tree 单链目录合并显示

> 一句话概括：**为在 workspace tree 中浏览深层嵌套目录的知识工作者，消除逐层展开单链文件夹的重复点击**

## 用户故事（Connextra）

作为 **在谨迹中浏览 workspace 文件的知识工作者**，
当我 **要打开一个位于多层单链目录（每层只有一个子文件夹、无其他内容）深处的文件**，
我希望 **这条目录链在树中显示为一个节点，一次展开直达内容**，
以便 **少点击、少占树的纵向空间，更快到达目标文件**。

## 真实用户问题（背景，讲故事）

Workspace 中（尤其是 Agent 产出物、按日期/主题分层组织的目录）常出现 `a/b/c` 式单链结构：每层只有一个子文件夹。当前树把每一层都渲染为独立可展开节点，用户必须逐层点击 N 次才能看到文件，且展开后树又高又窄、有效信息密度低。IDEA / VS Code 的 "compact folders" 是业界成熟解法，用户明确希望对齐该惯例。

[证据] 用户本人描述："多个文件夹自动收敛成一个，不用重复展开"。

### 现状失败模式

- 现在怎么解决：手动逐层点击展开，或忍受高而窄的树。
- 为什么不够好：到达 N 层单链下的文件需 N 次点击；展开后树占用 N 行只承载一条路径的信息。
- 基线：3 层单链 = 3 次点击、3 行。

## 成功标准（脊柱 Q4）

### 用户行为变化

- 到达 N 层单链目录下的文件：点击 N 次 → 点击 1 次。
- 同一路径在树中占用行数：N 行 → 1 行。

⚠️ 假设依据：直觉 + 业界惯例（IDEA/VS Code 默认行为）。用户即本人，日常使用中直接验证。

## 验收标准（Given-When-Then）

### AC-1 — 单链目录合并显示

- **Given** workspace 中存在目录 `a/b/c`，其中 `a` 仅含子目录 `b`、`b` 仅含子目录 `c`，`c` 内有文件
- **When** 用户查看 workspace tree
- **Then** 该链显示为一个节点，标签为 `a/b/c`（IDEA 惯例的路径分隔展示）
- **And** 点击该节点一次即展开显示 `c` 内的文件

### AC-2 — 链条断开条件

- **Given** 目录 `a` 下除子目录 `b` 外还有文件或另一个子目录
- **When** 用户查看 workspace tree
- **Then** `a` 独立显示为一个节点，不与 `b` 合并（合并仅发生在"每层恰好一个子目录且无其他内容"的链上）

### AC-3 — 结构变化后自动重算

- **Given** `a/b/c` 已合并显示为一个节点
- **When** 用户（或 Agent）在 `a` 下新增了一个文件或目录
- **Then** 树更新后 `a` 从合并节点中拆出，独立显示

### AC-4 — 合并节点上的操作对齐 IDEA 惯例

- **Given** `a/b/c` 合并显示为一个节点
- **When** 用户对该节点执行右键操作（新建/重命名/删除等既有菜单项）
- **Then** 操作语义与 IDEA 惯例一致：作用于链的最深层目录（`c`）；重命名/删除等需要指定层级的操作，以用户可理解的方式明确作用对象

## 三类边界（Won't）

- **不为哪些用户做**：无排除的用户群——workspace tree 的所有使用者统一生效。
- **不在哪些场景出现**：不影响 topic/journal 等非 workspace 文件树的其他侧栏区域；不合并"含文件的目录"或"多子目录的目录"（定义使然）。
- **不解决哪些相关但不同的问题**：不做用户可配置的开关（默认开、无设置项，v1 不做）；不做"点击合并标签中间段跳转到该层"的分段交互（IDEA 有但非核心，先不做）；不改变磁盘上的真实目录结构——纯展示层。
